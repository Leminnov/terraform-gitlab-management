# Security

## Reporting a Vulnerability

Please report security issues privately to the maintainers at `security@leminnov.com`. Do not open public issues for security reports.

## Secret Handling

### Inputs

Several module inputs carry values that are commonly secret:

| Variable | Secret fields |
|----------|--------------|
| `group_variables` | `value` (especially when `masked = true` or `protected = true`) |
| `project_variables` | `value` (especially when `masked = true` or `protected = true`) |
| `pipeline_schedules` | `variables` map values |
| `groups`, `projects` | `variables[*].value` |
| `projects` | `pipeline_schedules[*].variables` map values, `hooks[*].token` and `hooks[*].signing_token` |

The module sends every one of these values to the provider as a sensitive value, so `tofu plan` and `tofu apply` show `(sensitive value)` instead of the value, whether the caller passes a plain string or a `sensitive` variable. The inputs themselves are not declared `sensitive` because `for_each` iterates them (`DEVIATION(terraform-variables)` in `ci.tf`). Consumers should:

- Source secret values from `TF_VAR_*` environment variables set for the command only, a secrets manager (OpenBao, Vault, SOPS) or CI/CD secret variables; never hard-code them in `.tfvars` files committed to version control.
- Declare the caller's variables that hold them `sensitive = true`, as `examples/complete` does.

### What lands in state

Provider `gitlabhq/gitlab` 19.5 has no write-only (`*_wo`) argument and no ephemeral resource for any of the objects this module manages, so the following secrets are stored in state in plain text:

| Secret | Resource attribute | Why it is in state | Mitigation |
|--------|--------------------|--------------------|------------|
| Group CI/CD variable values, standalone and nested in `groups` | `gitlab_group_variable.this[*].value` | Required argument, no `value_wo` | Encrypted remote backend with restricted access; OpenTofu state encryption; mask and protect secret variables |
| Project CI/CD variable values, standalone and nested in `projects` | `gitlab_project_variable.this[*].value` | Required argument, no `value_wo` | Same as above |
| Pipeline schedule variable values | `gitlab_pipeline_schedule_variable.this[*].value` | Required argument, no `value_wo` | Same as above |
| Webhook secret and signing tokens | `gitlab_project_hook.this[*].token`, `gitlab_project_hook.this[*].signing_token` | Optional arguments, no `*_wo` | Same as above; one token per hook, rotated with the receiving endpoint |
| Group deploy tokens | `gitlab_group_deploy_token.this[*].token` | Generated by GitLab on create, returned once | Required expiry, at most one year (`token_lifetime` check); least scopes |
| Project deploy tokens | `gitlab_project_deploy_token.this[*].token` | Generated by GitLab on create, returned once | Same as above; one project only |
| Group access tokens | `gitlab_group_access_token.this[*].token` | Generated by GitLab on create, returned once | Required expiry, at most one year; lowest access level (`access_token_privilege` check) |
| Project access tokens | `gitlab_project_access_token.this[*].token` | Generated by GitLab on create, returned once | Same as above |
| Runner authentication tokens | `gitlab_user_runner.this[*].token` | Generated by GitLab on create, returned once | Rotate by replacement; register runners on protected refs where possible |
| Pipeline trigger tokens | `gitlab_pipeline_trigger.this[*].token` | Generated by GitLab on create | Rotate by replacement; one trigger per caller, so revoking one does not break the others |

### Outputs

Every output that carries a token is `sensitive = true`: `deploy_tokens`, `project_deploy_tokens`, `pipeline_trigger_tokens`, `gitlab_runner_tokens`, `group_access_tokens` and `project_access_tokens`. No output returns a CI variable value. Use `tofu output -json <name>` to read a token programmatically and store it straight in the system that consumes it; plain `tofu output` shows `<sensitive>`.

### Rotation

Rotate on schedule (before expiry, at most yearly), when someone who could read the secret leaves, and at once on exposure. A rotation is complete only when the old value no longer works.

| Secret class | Generated by | How to rotate | Consumers to update | Check the old value is dead |
|--------------|--------------|---------------|---------------------|-----------------------------|
| CI variable and schedule variable values | Their issuer (registry, cloud, API) | Issue a new credential at the issuer, change `value` in the caller's secret store, apply, then revoke the old one at the issuer | Pipelines pick the new value on their next run | The issuer rejects the old credential |
| Deploy tokens | GitLab, on create | Change `expires_at` or apply `-replace='module.<name>.gitlab_group_deploy_token.this["<key>"]'` (`gitlab_project_deploy_token` for a project token): GitLab revokes the old token and issues a new one | Whatever reads `deploy_tokens` / `project_deploy_tokens` (registry logins, CI variables of other projects) | `git ls-remote` or `docker login` with the old token fails |
| Group and project access tokens | GitLab, on create | Change `expires_at` or apply `-replace=` on the token's address | Whatever reads `group_access_tokens` / `project_access_tokens` | `GET /api/v4/personal_access_tokens/self` with the old token returns 401 |
| Runner authentication tokens | GitLab, on create | Apply `-replace=` on `gitlab_user_runner.this["<entry>"]`, then re-register the runner manager with the new token from `gitlab_runner_tokens` | The runner manager's `config.toml` | The old runner shows as never contacted and is gone from the runner list |
| Webhook secret and signing tokens | The caller | Generate a new token, set it on the receiving endpoint next to the old one, change `token` / `signing_token` in the caller's secret store and apply, then drop the old one at the endpoint | The endpoint that checks `X-Gitlab-Token` or `X-Gitlab-Signature` | The endpoint rejects a request signed with the old token |
| Pipeline trigger tokens | GitLab, on create | Apply `-replace=` on `gitlab_pipeline_trigger.this["<project key>:<description>"]`: the old trigger is deleted with its token | The caller holding the token from `pipeline_trigger_tokens` | `POST /api/v4/projects/<id>/trigger/pipeline` with the old token returns 404 |
| Integration sandbox tokens (`GITLAB_TOKEN`, `GITLAB_TOKEN_LEAST`) | A maintainer, on the sandbox group | Create the new group access token, replace the CI variable, run the `develop` pipeline, then revoke the old token | The project's CI/CD variables and the maintainer's secret store | `GET /api/v4/personal_access_tokens/self` with the old token returns 401 |

## State Security

The state of a root module calling this module holds every value listed above. Root modules must:

- Use a remote backend with encryption at rest (GitLab-managed Terraform state, S3 + KMS, GCS + CMEK, Azure Blob with encryption keys), or OpenTofu state encryption.
- Enable state locking.
- Restrict access to the state to the smallest set of principals required.
- Never commit `.tfstate` or `.tfstate.backup` to version control (the `.gitignore` covers it).

## Least Privilege

- Use the smallest `access_level` and `scopes` that satisfy the consumer's needs; the `access_token_privilege` check warns on `owner` and on an unset level, which GitLab turns into `maintainer`.
- Prefer project-scoped tokens over group-scoped tokens where project-level access suffices.
- Deploy keys are read-only unless `can_push = true`, and require an expiry. Grant access through `members` and `shared_with` at the lowest `access_level` that works, with an `expires_at` for temporary access.
- `job_token_allowlist` limits which projects' CI/CD job tokens can reach a project; set it on projects other pipelines must not read.
- Every deploy and access token has an expiry; the `token_lifetime` check warns beyond one year.
- The module validates expiry formats, scopes, access levels, runner IDs and non-empty `groups`/`projects`/`scopes`; see `variables.tf` for the accepted values.

## Supply Chain

- Tool versions (OpenTofu, tflint, terraform-docs, pre-commit, gitleaks, trivy, checkov, osv-scanner, git-cliff, openspec) are pinned in `mise.toml`, and the CI images in `.gitlab/` carry the same versions. Renovate (`renovate.json`) bumps a pin and its CI copies in one "toolchain" merge request.
- Every pipeline runs pre-commit (fmt, docs, tflint, validate, checkov, trivy, gitleaks on staged files), `osv-scanner`, `security:trivy` (misconfigurations, secrets and vulnerable dependencies) and the unit tests; merge requests also run `security:gitleaks` over their commits, and the weekly schedule runs it over the full history.
- Checkov findings suppressed inline, each with its reason next to the rule id (`projects.tf`):
  - `CKV_GLB_1` (required approvals), `CKV_GLB_3` (push rule `prevent_secrets`), `CKV_GLB_4` (signed-commit push rule): Premium features, which a Free namespace cannot enable. Premium namespaces set `approval_rules` and `push_rules`.
  - `CKV_GLB_2` (no force push): `allow_force_push` defaults to `false`, checkov cannot resolve the per-branch input, and `check.protected_branch_force_push` warns when a caller enables it.
- A release is a signed `vX.Y.Z` tag on `main`; its pipeline publishes a CycloneDX SBOM to the project's package registry, linked from the release, and `create:release` waits for every validation and scanning job.
