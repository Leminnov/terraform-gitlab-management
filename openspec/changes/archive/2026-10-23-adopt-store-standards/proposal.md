# Proposal

## Why

The repository now references the `quality`, `repository`, `terraform`, `git`, `gitlab`, `secrets` and `openspec` stores but meets few of their rules, and the module is about to break on its own provider:
- `gitlab_deploy_token` is deprecated in `gitlabhq/gitlab` 18.11 and removed in 19.0.
- Since 19.4, `gitlab_pipeline_schedule.ref` must be a full ref, so the documented `ref = "main"` fails.
- The access-token enums accept values the provider rejects (`no_one`, `sudo`, `admin_mode`, `read_user`) and reject `no one`, `planner` and `security_manager`, which it accepts.
- Every CI variable value is printed in clear in plan output, because the provider does not mark `value` sensitive.
- Deploy tokens can be created without expiry.

There are also process gaps:
- The changelog is regenerated by git-cliff instead of curated, and stops at 11.0.0 although `v11.1.0` and `v12.0.0` exist.
- Release notes come from raw commits, and a release asset is a job artifact that expires.
- CI jobs run with `when: always` and no workflow rules, timeouts or examples job.
- No integration test has ever applied the module.

This change fixes all of it in one major release, `v13.0.0`.

## What Changes

Module contract (semver **major** per `terraform-versioning`):
- **BREAKING** Provider floor raised from `gitlabhq/gitlab ~> 18.11` to `~> 19.5`. 19.0 removes `gitlab_deploy_token`, 19.1 adds the state mover that `gitlab_group_deploy_token` needs, and 19.5 is the version tested. `required_version >= 1.11.0` is unchanged. Provider 18.x fails at `init`.
- `gitlab_deploy_token.this` becomes `gitlab_group_deploy_token.this` with a `moved` block. Existing tokens are migrated in state by the provider, not recreated.
- **BREAKING** `deploy_tokens[*].expires_at` becomes required (`secrets-rotation`: no token without expiry). Setting it on an existing token makes GitLab issue a new token, which consumers must roll out.
- **BREAKING** `pipeline_schedules[*].ref` must be a full ref (`refs/heads/<branch>` or `refs/tags/<tag>`), validated at plan time. This matches provider 19.4+, which already rejects short refs.
- The access-token `access_level` and `scopes` enums are aligned with the provider. Found while applying: the provider always rejected the values the old enums accepted, so these are fixes with no consumer edit for a working config.
  - `access_level` accepts `no one`, `minimal`, `guest`, `planner`, `reporter`, `security_manager`, `developer`, `maintainer` and `owner`.
  - `scopes` follow each resource's list. `read_user`, `sudo` and `admin_mode` are rejected; `read_observability` and `write_observability` are accepted.
  - Access-token `expires_at` must be `YYYY-MM-DD`, and deploy-token `expires_at` an RFC 3339 timestamp: the only form each resource parses. Providers 18.11 and 19.5 both reject a bare date on deploy tokens.
- `gitlab_runners[*].group_id` and `project_id` must be numeric IDs, since the provider attribute is a number. Paths used to fail at apply; they now fail at plan with the module's message.
- Fixed `gitlab_runners` (and the removed `gitlab_runners_by_type`): it read `runner_id` and `status`, which `gitlab_user_runner` does not have, so v12 failed to plan any runner. Found while applying.
- **BREAKING** 13 outputs are removed because they duplicate another output or echo inputs back:
  - Duplicates: `deploy_tokens_by_group`, `deploy_tokens_summary`, `gitlab_runners_by_type`, `group_access_tokens_by_group`, `group_access_tokens_summary`, `project_access_tokens_by_project`, `project_access_tokens_summary`, `all_tokens` and `resource_counts`.
  - Input echoes: `group_variables`, `project_variables` and `pipeline_schedule_variables` (secret values) and `pipeline_schedules` (`pipeline_schedule_ids` keeps the IDs).

  They are removed rather than deprecated, by maintainer decision (`DEVIATION(repository-versioning)`).
- CI variable values and pipeline schedule variable values are wrapped in `sensitive()`, so plan output shows `(sensitive value)`. The input shape is unchanged. The inputs themselves cannot be `sensitive = true` because `for_each` iterates them (`DEVIATION(terraform-variables)`).
- New plan-time warnings (`check` blocks):
  - a CI variable whose key looks like a secret but is not both masked and protected;
  - a token expiring more than a year after the plan;
  - an access token with `owner`, or with no `access_level` (GitLab then defaults to `maintainer`).
- Removed a redundant `depends_on` on `gitlab_pipeline_schedule_variable`.

What lands in state: CI variable values, schedule variable values and every token GitLab creates (deploy, access, runner). Provider 19.5 has no write-only argument on any of these resources, so no secret-bearing input can follow the `*_wo` pattern. `SECURITY.md` lists them in a "what lands in state" table with mitigations.

Tests:
- The unit suite moves to `mock_provider "gitlab"`. It gets a rejected-input run for every validation block, a run per `check`, assertions on redaction (`issensitive`) and the expected output keys.
- New integration fixture `tests/integration/`, run against a sandbox group on gitlab.com in three modes:
  - **owner** and **least privilege**: apply, server-side assertions, no secret in plan output, empty second plan, destroy.
  - **upgrade**: apply with `v12.0.0` and provider 18.11, then plan with this module and 19.5. The plan must not replace any deploy token.

  It is run by `mise run test-integration` and by CI on protected refs.

Repository conformance:
- Tooling: exact pins aligned with the keycloak module plus checkov and osv-scanner; unused `age`, `sops`, `shfmt` and `yamlfmt` removed; `min_version`; descriptions on every task; `test`, `scan` and `test-integration` tasks.
- Changelog and releases: `changelog` is replaced by `changelog-draft`, `changelog-verify` and `release` (`scripts/release.sh`, `scripts/changelog.sh`). `CHANGELOG.md` is curated by hand from now on, with `11.1.0` and `12.0.0` backfilled. Release tags are signed.
- Hooks and config files:
  - `.pre-commit-config.yaml` gets the canonical general hooks plus pre-commit-terraform `v1.109.1` (validate, checkov and trivy, `--tf-path=tofu`). The extra general hooks and `no-commit-to-branch` are removed.
  - New files `.terraform-docs.yml`, `.trivyignore.yaml` and `.gitattributes`; the tflint ruleset is pinned.
  - `.gitignore` and `.editorconfig` match the canonical files.
  - `.gitleaks.toml` replaces its blanket path allowlist with entries per finding, each with a reason.
- CI:
  - `workflow: rules`, `interruptible`, timeouts, and `needs:` expressing the dependencies.
  - `validate:opentofu` runs a matrix (minimum and pinned version) with `tofu test`, plus `validate:examples`.
  - `security:trivy` publishes an SBOM to the package registry; `security:gitleaks` scans the merge request diff, and the full history on the weekly schedule.
  - `verify:changelog` runs `scripts/release.sh check`.
  - `create:release` publishes the curated changelog section as notes, gated on every job. The expiring `SHA256SUMS.txt` asset is dropped; signed tags and the SBOM replace it.
- Cleanup: `.github/` (stale GitHub Actions), `RELEASE.md` and `CONTRIBUTING.md` are removed; their still-valid content moves into the README Releasing and Contributing sections. In `renovate.json`, `:semanticCommits` is removed (`git-commits`) and the regex managers are fixed: all four mapped to `jdx/mise`.
- Docs:
  - README follows `repository-readme` and `terraform-repo-readme`: title, provider badge, the correct release badge path, Requirements and compatibility table, Basic, Complete and Conditional examples on `?ref=v13.0.0`, Security Considerations, Known Limitations, Contributing, Releasing and Disclaimer.
  - Examples get `providers.tf`, secrets from variables without defaults, and no `timestamp()` (it caused a perpetual diff).
  - `SECURITY.md` gets the state table, least-privilege token roles and rotation procedures; `TESTING.md` covers both suites.
  - `AGENTS.md`, `CLAUDE.md` and `openspec/config.yaml` are updated to the new commands and conventions.

Out of scope:
- Project deploy tokens (`gitlab_project_deploy_token`), `rotation_configuration` on access tokens, the `hidden` and `environment_scope` variable attributes, and service-account tokens.
- Renaming inputs (`gitlab_group_access_token` and similar).

## Capabilities

### New Capabilities
- `module-contract`: supported OpenTofu and provider versions, no provider or backend blocks, fan-out keys, what is redacted in plans and what lands in state, the output set, empty second plan.
- `ci-variables`: group and project CI/CD variables: fan-out across targets, key format, variable type, protected and masked flags.
- `deploy-tokens`: group deploy tokens: fan-out, required expiry, scopes, migration from `gitlab_deploy_token`, token output.
- `access-tokens`: group and project access tokens: fan-out, access levels, scopes and expiry format aligned with the provider, token outputs.
- `pipeline-schedules`: pipeline schedules and their variables: full ref, cron form, redacted variable values, schedule IDs.
- `runners`: runners created with `gitlab_user_runner`: runner type and owning group or project, access level, tags, timeout, runner tokens.
- `security-guardrails`: plan-time `check` warnings for dangerous but legal configurations.

## Impact

- Consumers must:
  - upgrade the provider to `~> 19.5` (`tofu init -upgrade`);
  - add `expires_at` to every deploy token, then roll out the replaced token;
  - write schedule refs as `refs/heads/<branch>`;
  - use `no one` instead of `no_one` and drop the `read_user`, `sudo` and `admin_mode` scopes;
  - pass numeric runner group and project IDs;
  - move any reference to a removed output to its replacement.

  Upgrade notes go in `CHANGELOG.md`.
- State: the `moved` block migrates deploy tokens through the provider's state mover. Token values, variable values and runner tokens stay in state, as before.
- Server: tested on gitlab.com. `instance_type` runners need an admin token and are covered by unit tests only.
- Files:
  - Module and tests: `*.tf`, `checks.tf`, `tests/`, `tests/integration/`, `examples/`, `scripts/`.
  - Repository and CI: every repository and CI file listed above, `renovate.json`, `CODEOWNERS`.
  - Docs and planning: README, `SECURITY.md`, `TESTING.md`, `CHANGELOG.md`, `AGENTS.md`, `CLAUDE.md`, `openspec/config.yaml`.
  - Removed: `.github/`, `RELEASE.md`, `CONTRIBUTING.md`.
- GitLab, done by a maintainer outside the repository:
  - Sandbox group and project with two protected, masked, expiring tokens.
  - Weekly pipeline schedule on `main`.
  - Protected `v*` tags; protection on `main` and `develop`; merge request settings.
  - The public visibility recorded in the project description.
  - A decision on the default branch (`develop` today; `gitlab-project-settings` says `main`).
